# 多会话资源保护与压测

2026-10-03，Desktop 已接入共享资源额度和空闲回收。历史聊天本身不启动 Kimi；第一次执行才申请执行与常驻额度。任务完成后可保留原生进程复用，空闲到期或需要让出额度时关闭，下一轮按原 session ID 和持久目录恢复 Kimi 上下文。

## 默认策略

| 保护             | 默认值    | 到达边界时的行为                                                    |
| ---------------- | --------- | ------------------------------------------------------------------- |
| 同时执行的会话   | 4         | 明确拒绝新任务，保留可重试记录，不启动新 Kimi 或发送模型请求        |
| 常驻原生会话     | 6         | 请求回收最久未使用的空闲会话，确认关闭后再允许新进程占用位置        |
| 空闲期限         | 5 分钟    | 关闭空闲 Kimi，释放会话的观察数据库连接；聊天、日志和原生上下文保留 |
| 可用内存保留量   | 256 MiB   | 拒绝新任务并请求回收空闲会话，不强行终止正在运行的任务              |
| 等待常驻额度释放 | 最多 5 秒 | 关闭仍未完成时明确拒绝，避免无限等待或提前释放额度                  |

运行中、等待审批、等待回答的会话占用执行额度，不参与自动回收。Stop 优先使用 Kimi 中断；3 秒后仍未结束则关闭该原生会话，确认关闭后取消本轮，结束后才转为空闲。关闭应用会等待所有会话关闭和额度释放，再退出，即使其中一个关闭失败也会等待其他会话完成。

如果在等待常驻位置释放时点击 Stop，会记住取消请求，取得位置后直接结束本轮，不再启动原生 Prompt。

额度存储在配置目录中的 `session-resources.sqlite`，默认目录为 `~/.industrial-agent-harness`。使用同一目录的多个 Desktop 窗口与 CLI 进程，通过 SQLite 事务共享额度。宿主设置不同限额时，执行/常驻数量取存活宿主的最小值，内存保留量取最大值。已退出宿主按 PID 存活检查清理。独立配置目录代表明确隔离的实例，不共享额度。

回收由资源所属宿主完成。跨宿主申请容量只写入回收请求，不关闭其他宿主的运行中会话。回收失败和关闭过程中仍占用额度。管理器只处理宿主资源生命周期，不接管 Kimi 的模型/工具循环、上下文或压缩。

## 配置

在启动 Desktop 前设置环境变量，两者使用相同规则：

| 环境变量                                     |      默认值 |
| -------------------------------------------- | ----------: |
| `INDUSTRIAL_HARNESS_MAX_CONCURRENT_SESSIONS` |         `4` |
| `INDUSTRIAL_HARNESS_MAX_RESIDENT_SESSIONS`   |         `6` |
| `INDUSTRIAL_HARNESS_SESSION_IDLE_MS`         |    `300000` |
| `INDUSTRIAL_HARNESS_MIN_FREE_MEMORY_BYTES`   | `268435456` |

数量和空闲期限必须为正整数，常驻上限不得小于执行上限；内存保留量可设为 `0`，显式关闭内存准入检查。非法配置直接报错。`INDUSTRIAL_HARNESS_CONFIG_DIR` 沿用已有配置目录覆盖行为；每个任务设置不同目录不能共享额度。

Linux 使用 `MemAvailable`；macOS 使用 `vm_stat` 的 free、inactive、speculative 页面估计可用量，避免把可回收页面全部视为内存耗尽；Windows 使用系统空闲内存值。结果在宿主内缓存一秒，探测失败保守退回 `os.freemem()`。这是准入时的内存估计，不是进程内存配额。

## 实测结果

16 GiB macOS arm64、Node 25.9.0，固定 SDK 0.1.8 / Kimi CLI 1.51.0。两个独立 Node 宿主共用额度，真实原生进程连接本地可控 OpenAI 兼容端点，没有远端模型费用或真实工程修改。[原始结果](session-resource-stress.json)由 `scripts/stress-sessions.cjs` 生成。

| 观察                      | 旧生命周期基线 |           启用保护 |
| ------------------------- | -------------: | -----------------: |
| 同时提交的任务            |             12 |                 64 |
| 首轮启动 / 拒绝           |         12 / 0 |             4 / 60 |
| 之后按序执行的轮次        |             12 |                 12 |
| Kimi 进程峰值             |             12 |                  6 |
| Kimi RSS 采样峰值         |   1,629.70 MiB |         842.89 MiB |
| 宿主及子进程 RSS 采样峰值 |   1,738.75 MiB |       1,023.48 MiB |
| CPU 百分比采样峰值        |         650.6% |             390.4% |
| 空闲回收后的 Kimi 进程    |             12 |                  0 |
| 原生会话 ID 与历史上下文  |           保留 | 回收后恢复验证通过 |

保护组的执行额度峰值为 4、常驻额度峰值为 6；轮换后共回收 12 次。回收后模型请求仍包含先前的用户标记和 Assistant 回复，验证恢复来自 Kimi 原生上下文。

为保护测试机器，基线只同时启动 12 个进程；保护组同时提交 64 次，超额请求按设计拒绝。两组负载不同，不能将资源对比解释为相同吞吐量下的性能提升。采样约每 150 ms 一次，RSS 不等于总内存占用，CPU 是 `ps` 平滑估计，100% 表示一个逻辑核；可能漏掉更短峰值。压测将空闲期限加速为 750 ms，生产默认仍为 5 分钟。

## 验证与适用范围

- Core 测试覆盖共享与更严格额度、重复释放、主动与交互等待保护、空闲到期、跨宿主回收、慢关闭、回收失败、死亡宿主、内存不足和可回收内存估计。
- 真实 Kimi 集成检查运行中的会话超过空闲期限仍存活，独立 CLI 超限时不发送模型请求，回收后以同一 ID 恢复上下文，以及 CLI 请求另一个宿主释放空闲位置。
- macOS Desktop 并行回归以 100 ms 空闲期限运行，后台审批、跨项目并行、Stop 和回复隔离通过；重启恢复、日志与既有 CLI/MCP 路径继续通过。

该保护限制被管理的 Kimi 会话数量，不是操作系统级 CPU/RSS 硬隔离。一个会话仍可能启动很大的工业工具、MCP 或其他子进程；这些工具的资源限额属于独立运行时。本次未重新验证 Windows/Linux 包装流程，也未做真实工业工作负载验收。

## 复现

```bash
pnpm test
pnpm test:architecture
pnpm test:session-resources
pnpm test:session-chaos
INDUSTRIAL_HARNESS_SESSION_IDLE_MS=100 pnpm --filter @industrial-agent-harness/desktop test:parallel
pnpm stress:sessions
```

真实测试需要固定 Kimi CLI，可设置 `KIMI_EXECUTABLE`。压力采样支持 macOS/Linux 的 `ps`；基线比较要求至少 2.5 GiB 估计可用内存，运行中低于 512 MiB 则停止。所有会话和配置建立于独立临时目录，结束后关闭测试进程并清理。

## 切换与交错操作验证

2026-10-03 按用户要求补充频繁切换和异常操作测试。切换只改变当前展示的聊天，后台任务继续执行；4 个是执行上限，不是可打开的历史数量。审批、回答和 Stop 绑定生成按钮时的聊天；切换进行中暂时禁用操作，同一帧的连续点击只发起一次切换。打开聊天和刷新列表不创建运行对象，也不启动 Kimi。

历史回复携带宿主内的事件序号。读取期间收到的更新会与快照合并，只接受快照之后、同一聊天和同一轮的事件，避免回复重复、已结束任务恢复为运行中、失效审批重新出现。序号只用于当前窗口的显示协调，不改写 Kimi 上下文或聊天持久格式。临时缓冲最多 4,096 个事件，超过后重新读取历史；旧聊天导航的异步结果不会覆盖新选择。

补充的 macOS Electron 测试实际操作生产 Renderer、IPC、ChatStore 和资源管理器，用可控 SDK 会话故意保留审批、问题和旧历史响应：

- 4 个后台任务跨越 100 ms 空闲期限仍受保护，第 5 个任务明确拒绝且不进入内核。
- 160 次同一帧双击聊天，加上 40 次跨项目切换，共 200 次切换；每次检查后台任务数仍为 4、选中聊天与宿主一致。
- 4 个任务运行时重载 Renderer，恢复当前问题；回答和连续两次 Stop 不影响其他聊天，原生中断各执行一次。
- 故意延迟运行中的历史快照，先完成实时回复、再送达旧快照；最终没有重复回复、活动审批或错误的运行状态。
- 删除结束的聊天，再启动一个等待审批的任务，并让正常应用退出流程关闭它；测试进程以 0 退出。

另一个测试使用真实固定 Kimi CLI：先保存上下文，在新一轮请求中 SIGKILL 第一个 Kimi，保持第二个 Kimi 等待。固定 SDK 0.1.8 的信号退出路径会留下未完成的结果等待；这是已复现的集成边界，本次未修改 SDK。连续 Stop 触发生产默认 3 秒兜底，实测约 3.01 秒结束第一轮，第二轮继续并正常完成。第一聊天随后用相同原生 ID 恢复，模型请求仍包含先前已落盘的用户标记。

该兜底由 Stop 或应用关闭触发，不把信号退出自动判定为已完成，也不自动重试可能产生修改的任务。恢复验证只覆盖已落盘的上下文，不承诺强杀时尚未落盘的最后片段。测试结果见 [交错操作结果](session-chaos-results.json)。

失败路径单测还验证：设置重置期间占住目标聊天、慢关闭不会被其他会话的早期错误跳过、历史写入或事件观察失败仍释放宿主执行/Pack 额度。后台收尾错误被显式捕获，防止未处理 Promise 拒绝传播到应用。

2026-10-05 迁移到 Kimi Code 2.1.1 后，真实进程死亡立即报告失败并释放执行额度，重复 Stop 仍安全；同一身份的已落盘上下文和另一聊天均保留。上述 SDK 0.1.8 的 3 秒信号问题及压测数字属于旧内核证据，新版本范围见 [迁移记录](kimi-code-migration.md)。
