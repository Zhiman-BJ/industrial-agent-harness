# 27B / 256k 上下文适配计划

状态：2026-09-25，第一阶段在本 PR 实施。目标是提高长工业任务的上下文利用率与可诊断性，同时继续由固定版本的 Kimi Code 负责 Agent Loop、工具循环、会话历史和压缩。

## 现状与风险

- 模型配置允许声明 `max_context_size = 262144`，但窗口大小不能证明模型能可靠使用窗口内任意位置的信息。模型名称和真实服务端限制由部署环境决定。
- Harness 在每轮提示词中放入 Broker Scope；Scope 的随机版本号变化会导致 Kimi 会话重建，即使可用能力没有变化。
- Harness 的外部工具直接返回完整 JSON。界面上的 12,000 字符截断只影响事件显示，不限制传给模型的内容。Kimi 原生文件、Shell 和 MCP 工具不经过这一边界。
- 已有 `StatusUpdate` 与压缩事件，但缺少每轮汇总，无法从 bench 输出快速判断压缩前后的上下文压力或异常大的工具结果。
- 当前缺少持久化的 DomainState、Action、Artifact Registry 和 Checkpoint。不能把会话摘要当作可信工程事实。

## 第一阶段：本 PR

1. **外部工具输出边界**：Harness 注册的能力详情和工件元数据工具最多返回 16 KiB UTF-8 JSON。超限时明确失败，不静默截断事实；能力详情支持按 skills、tools、verification 分段读取。每次调用继续检查当前 Broker Scope，元数据仍由调用方验证工件哈希。
2. **提示词边界**：每轮 Industrial Context 最多 8 KiB；超限时要求缩小 Broker Scope。用户任务文本不在这一限制内，也不被改写。
3. **稳定会话判定**：比较实际生效的 domain、stage、capability、skill 和 tool，而不是随机 Scope 版本。有效 Scope 或模型配置变化时仍重建会话；每轮都重新注入当前 Scope。
4. **可观测性**：汇总 SDK 报告的上下文占用峰值、末值、压缩次数、工具结果数及最大结果字节数，在 CLI JSONL 与桌面调试流中呈现。界面截断工具结果时明确标记，避免误以为显示的是完整结果。这些值只用于诊断，不自动触发新的压缩。
5. **验证**：使用固定 SDK 版本的工具定义做单元测试；模拟 SDK 事件验证会话复用、真实 Scope 变化后的重建、压缩及结果大小统计；运行全量测试、架构门禁和桌面构建。没有真实 27B 服务时，不宣称模型质量或真实压缩效果已验证。

## 后续阶段：依赖 Industrial Core Vertical Slice

1. 在 Domain Runtime 落地后，从持久化的 DomainState、Action、Artifact、Verification 和 Checkpoint 生成短且可追溯的工程状态锚点。Scope 重建与压缩后按需重新读取这些事实；保留来源 ID、输入哈希和验证状态，不从聊天文本推断工程结论。
2. 用真实 27B 模型建立长任务评测：包含大工具输出、关键事实位于长历史中段、Scope 切换、自动压缩、失败后恢复。比较任务完成率、事实遗漏、工具调用次数、延迟和 token 消耗。记录模型实际支持的输入、输出限制。
3. 只有评测证明 Kimi 原生压缩反复丢失关键工程状态时，才研究 SDK 提供的手动压缩或配置接口。任何改动先验证固定的 Kimi SDK 和 CLI 版本，不直接 fork 压缩实现。

## 第一阶段验收

- 超限的 Harness 工具结果不会作为完整成功结果进入模型；允许的分段结果仍可取得。
- 同一有效 Scope 的重新解析不会清空会话；实际 Scope 变化仍隔离旧工具权限。
- CLI 与桌面事件能区分模型可见结果大小和界面显示截断，并能看到每轮上下文与压缩汇总。
- 本 PR 不声称已解决跨进程持久化或 27B 长任务的模型质量；这两项以 Vertical Slice 和真实评测为后续门禁。
